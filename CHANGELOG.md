- feat(cli): `aristo rename <old_id> <new_id>` (without `--dry-run`) actually applies the plan to disk (slice 32 commit 4). Apply order is load-bearing: source files first (each file rewritten in memory then atomic temp+rename; same-file edits applied highest-byte-first so earlier byte offsets stay stable), THEN per-id artifact moves (`.aristo/critiques/<id>.critique`, `.aristo/proofs/<id>.proof` via `fs::rename`), THEN the new `.aristo/index.toml` LAST (also atomic temp+rename). The reason: if source writes complete but artifact-move or index-write fails, source has the new ids but the index still references the old ones — `aristo stamp` then detects structural drift and refuses, letting the user revert or complete manually. The reverse order would leave the user with an index pointing at ids the source doesn't define, making `aristo show` / `aristo list` lie. No real transactional rollback ships in slice 32 (out-of-scope per HANDOFF); "best-effort recoverable" is the contract. Source rewriting is byte-substitution at the `scan_id_occurrences` spans — whitespace, comments, and the rest of every file are byte-identical to before (verified by an explicit `assert_eq!(post, src.replace(old_quoted, new_quoted))` regression test). Index rewriting walks every entry, swapping the self-key for the renamed entry and rewriting every child `parent` link (single + array forms; array siblings preserved verbatim). Success line: `ok: renamed \`<old>\` → \`<new>\` (N source edits, K parent references, P artifact files)`. F1-c opaque-to-local promotions get the extra note: `note: promoted opaque id → readable id. Future references to \`<old>\` will fail. Update any external dashboards / links.` Dogfooded end-to-end on the SDK's own index: round-tripped `scan_id_occurrences_byte_spans_round_trip_exactly` → `find_id_occurrences` → back, confirming the source file remains byte-identical and the index re-parses. 6 new unit tests (24 total for the module) cover: id-byte-range substitution; parent-array element substitution with sibling preservation; whitespace + comment preservation across multi-line annotations; index self-key swap + child parent-link rewrite; artifact-file rename when present; parent-link rewriter leaves unrelated arrays intact. ### Added
- feat(cli): `aristo doc --include-graph` embeds the annotation graph in `_summary.md` (slice 29, commit 10 of 12). Composite flag that implies `--summary` and additionally appends the rendered annotation graph (Mermaid `flowchart TD` block) to `.aristo/doc/_summary.md` under a `## Annotation graph` heading. Mermaid renders inline in any markdown viewer that supports it (GitHub READMEs, Mermaid-aware rustdoc themes); no Graphviz dependency. Idempotent: re-runs always re-write the summary first then append the graph, so the final file has exactly one summary section + one graph section regardless of prior state. Conflicts with `--check` (read-only mode can't write the graph block). Intent `doc_include_graph_appends_idempotently` encodes the ordering rule. Promoted `doc_include_graph.md` scenario.
- feat(cli): `aristo graph --include-status` switches color axis to B5b status (slice 29, commit 9 of 12). New `--include-status` flag swaps the rendered color axis from verify level (default; for documentation use) to current B5b status (for "what's still unverified" review meetings). New `ColorAxis` enum drives a unified `NodeClass` selection in both Mermaid and DOT emitters. Status palette covers all 10 Status variants — Verified (green), Tested (blue), Neural (yellow), Stale (orange), Orphan (purple), Forged (red border), Unknown / PendingDeepen (gray), Counterexample / Inconclusive (red/orange + bold border). In status mode the palette already differentiates critical states via its own borders, so the verify-mode "critical" overlay is suppressed to avoid double-stacking. Verify level moves to the in-node label suffix `(intent, verify=X)` so it's still legible. Promoted `graph_include_status.md`. `StatusClass::from_status` is the single source of truth for the verify-to-status enum mapping.
- feat(cli): `aristo graph --include-orphans` flag + default-omit for the unfiltered view (slice 29, commit 8 of 12). New `--include-orphans` opts in to rendering intent nodes that are graph-orphans (no parent link AND no child links). Default OMITS them — they're usually atomic load-bearing claims that don't add visual structure to the graph (the aristo codebase itself currently has 80+ of them; without omission the default render is a node-cloud). Assumes are ALWAYS included regardless of graph-orphan status — they're contextual "ground" facts (see `--exclude-assumes` for the separate opt-out covering that population). Critical refinement: orphan-omission only fires for the unfiltered view. When `--filter` is present the user has explicitly asked for those nodes; dropping post-filter "orphans" would be a confusing footgun. 2 new unit tests: drop_orphan_intents_removes_standalone_intent_keeps_connected (positive case), drop_orphan_intents_keeps_assumes_even_when_orphan (assume-exemption). SVG integration test updated to pass `--include-orphans` since its 1-node fixture is an orphan.
- feat(cli): `aristo graph --depth=N` walks N hops of graph context around filter-matched nodes (slice 29, commit 7 of 12). New `--depth <N>` flag expands the filter-matched set with ancestors (via parent links) AND descendants (via reverse-edge traversal) within `N` hops. Implementation builds a reverse index `parent_id → [child_ids]` once for O(1) descendant lookup, then BFS from each matched node with a per-node hops-remaining counter. `--depth=0` is the no-op identity (same as omitting the flag). `--depth=999` is effectively unbounded for any realistic codebase. Only meaningful with `--filter`; without a filter the default scope is already the whole index. 4 new unit tests cover: depth=0 returns matched unchanged, depth=1 picks up immediate descendants, depth=1 picks up immediate ancestors, depth=N bounded correctly via a 3-node linear chain (a → b → c) where depth=1 from a reaches b but not c, depth=2 reaches c. The pending scenarios `graph_filter_direct_children.md` and `graph_filter_subtree.md` use spec annotation IDs (`aristos:balance_no_duplicate_cells`) that don't match the simple 3-node fixture; they stay in `_pending/` until a larger fixture exists or they're rewritten against the shared fixture shape.
- feat(cli): `aristo graph --exclude-assumes` opt-out flag (slice 29, commit 6 of 12). Drops assume nodes from the rendered graph. Default INCLUDES assumes — they form the "ground" of the property graph and dropping them by default would hide load-bearing background facts (the spec's load-bearing semantic). Useful when the question is "what's the verified-property structure" and OS / library assumptions are noise. Composes with `--filter` (filter runs first, then drop-assumes prunes the remainder). Promoted `graph_exclude_assumes.md`.
- feat(cli): `aristo graph --filter` J2 unified-grammar integration (slice 29, commit 5 of 12). New `--filter <key>=<value>` flag is repeatable; multiple `--filter` clauses AND together. Reuses the J2 parser from slice 18 verbatim — supports `id=<id>`, `file=<path>[:<LO>-<HI>]`, `parent=<id>`, `status=<state>`. Default scope (no filter) is the whole index, unchanged. The slice-29-MVP shape is exclusion-only: filtered-in nodes render, filtered-out nodes (and their edges) are dropped. The mockup's "+ immediate external parents for context" auto-expansion lands as part of commit 7's `--depth` semantics. 7 unit tests in `mod.rs` cover id/file/parent/status filters, AND composition, no-match empty result, and the `site_line` parser helper.
